# 禁止转发下的起播准备验收

日期：2026-11-23，Asia/Shanghai。用户仍报告飞牛 `STRM 直连播放异常（-99985）`，明确以授权公网部署的实际播放成功作为完成标准。之前的本机或合成素材通过不能代替该标准。

## 实际发现

重新登录授权公网账号，确认禁止转发仍开启。测试账号最初只有上轮验收留下的记录，不能用来归因用户此次手机的失败。通过正常的剧集详情和继续播放入口，本机飞牛直接连接公网，当前爱奇艺来源能显示真实剧集画面；该结果仅覆盖当时的来源与本机客户端。

其他来源实查：红牛清单包含 AES-128；虎牙清单返回 HTTP 444；暴风媒体已失效。魔都和无尽的首分片分别返回有效的 206 MPEG-TS 数据，公网重新识别魔都第一集得到 1920×1080、H.264、25 fps。此前图片头来源需要在清单返回前准备数百个区间，首次识别延迟可能超过客户端等待时间。

实际 `1.13.0 / 1130013` 的 STRM 界面可能没有手动来源按钮。协议对照还发现，改变协商字段虽然能出现来源标签，换源后画面和进度可能留在旧来源。另一种原生 HLS 路径能出画，但受控分片请求携带了本站登录头。这些实验只连接本机合成服务，不作为可发布修复。

## 修复行为

保持原有 STRM 空媒体请求头和全局禁止转发规则，在起播前完成来源准备：

- 当前 HLS 读取并解压有界清单，检查媒体或会话密钥，解析子清单，准备图片头分片的真实区间；普通首分片最多检查 4 KiB。每条来源限三秒。
- 当前来源不能完成准备时，在八秒内寻找账号获准使用、同作品和同集、已有真实视频探测结果的替代来源。替代来源也检查清单和首分片。未知年份的不同条目不自动合并。
- 返回目标来源自己的媒体身份和进度；在 `play/info` 和后续 `stream` 之间传递说明，播放日志记录实际选择和失败原因，不伪造原来源成功。
- 已确认失效、图片或被拒绝的备选不再进入菜单。显式选择的来源不被再次自动替换。没有确认可用的替代时不更换剧集、不复制进度、不开启转发。
- `/api/health`、`/api/me` 增加实际构建的 `build_revision`，CI 将发布提交注入二进制，避免多个修复均显示相同包版本而无法确认部署。

## 验证

Rust 集成测试 71 项、AES 单元测试 2 项，共 73 项通过；Clippy 将警告视为错误，格式检查和本地构建通过。新增回归覆盖：加密来源切换到同集未加密来源、目标独立进度、管理员限定来源不泄露、HTTP 444 起播前替换、失效备选过滤、显式选源保持及正常原生调用流程中的说明传递。原有并发区间识别测试清空预检缓存后继续覆盖真正的并发冷识别；失效分片每次显式读取仍只有一次请求。

当前源码在独立服务中未经响应改写地验证。本机飞牛 `1.13.0` 使用新账号身份和新作品，默认来源为加密 B，B 的初始进度 89 秒，未加密 C 的初始进度 7 秒。正常点击继续观看后，实际 `play/info` 返回 C 的媒体身份和 7 秒，`stream` 交付 C；客户端显示 C 的蓝色画面，进度持续回传。记录到 17 次客户端媒体请求，Cookie、Authorization、Authx 均为零，方式保持 `direct`；B 的记录保留为 89 秒。长分片样本中的客户端定位不作为精确拖动或实体 iPhone 验收。

证据在忽略的 `tmp/fntv-public-goal-20261123/`，当前源码客户端证据为 `current-code-native-evidence.json`，独立素材和请求日志位于 `tmp/fntv-native-final-20261123-E9LlRW/`。前面的协议实验、旧身份缓存及成功字段不能计入最终验收。凭据、登录会话、数据库、真实媒体地址和影片截图不提交。

## 公网完成标准

发布镜像、更新运行端和客户端出画分别确认。只有公网健康接口返回本次提交的 `build_revision`，并且通过正常客户端入口实际播放、持续回传进度、保持禁止转发，才达到用户本轮的公网完成标准。本地已通过的结果不代表公网已完成；当前未取得服务器部署入口，测试账号不具备容器管理能力。
