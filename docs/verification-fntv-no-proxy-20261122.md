# 禁止转发与飞牛客户端播放方式显示验收

日期：2026-11-22，Asia/Shanghai。用户报告开启“禁止转发”后飞牛提示“文件权限不足”，截图同时显示异常的 `28p · 28 × 28 · PNG`，并要求在客户端看到直链或转发状态。

## 故障与修复

独立数据库、本机客户端和正常受控 HLS 下复现相同的“文件权限不足”。飞牛的普通 HLS 原生通道也会读取 `/v/api/v1/media/range/{guid}`，现有实现将其作为转发入口；全局禁止转发随即返回 403。首次请求中的 SDK UUID 尚未与菜单绑定，又会进入通用 NAS 转发分支。因此，这是播放协议交付与禁止转发规则之间的冲突，不是本地文件权限不足的证据。

禁止转发时，HLS 通过 STRM 交付带 `.m3u8` 后缀的独立来源地址，媒体请求头为空，入口只生成指向上游的主清单。客户端直接取得上游清单与分片。认证媒体请求、NAS 重试及已有转发资源仍受全局开关限制，不通过返回外部清单来放行带本站登录头的请求。

STRM 默认读取直链列表首项，因此将本次选择的 HLS 来源固定为首项，其他来源保留原画质顺序。初始参考集确定列表顺序，后续按直链索引或原生选择码切换时都定位到相同媒体；当前标签、选择码与媒体身份保持一致。SDK UUID 在首次认证媒体读取前绑定，换源、退出及进度继续按实际播放会话处理。全局禁止转发后重新起播不会复用尚未交付的旧转发重试。

客户端原有的文件名称、文件位置和视频标题加入播放方式。详情的“文件位置”在起播前显示 `直链（待播放）` 或 `转发（待播放）`，已有活动会话时采用会话的实际方式；播放协商同时记录所选方式。来源按钮仍使用短名称，未追加状态或画质后缀。

PNG 图片头后确认连续 MPEG-TS 同步字节时，元数据探测使用 MPEG-TS 解复用器，排除封面流。旧的仅含 PNG 的探测缓存重新识别，确实返回图片的地址或分片明确提示刷新、换源。此修复覆盖两类已构造的错误样本，未据此断言用户原片源一定采用图片头伪装。

## 本机客户端验证

故障排查开始时运行的是 `1.12.3 / 1123003`，测试期间本机安装更新为 **1.13.0 / 1130013**。以下最终结果来自后者，运行于 Mac 的 iOS 兼容环境，连接独立本地服务和受控媒体。

- 开启禁止转发后，普通 1080p HLS 实际显示蓝色画面。最终阶段快照取得 **14 次媒体读取、10 次进度回传**，当前会话方式为 `direct`、来源为“本地源C”；媒体请求中的本站 Cookie、Authorization、Authx 数为 **0**。
- 客户端详情的“文件位置”分别实际显示 `/播放方式/转发（待播放）/...` 和 `/播放方式/直链（待播放）/...`，不是只验证 JSON 字段存在。
- 受控 AES-128 HLS 在 STRM 直连下仍提示 **-99985**；允许转发后原生解密路径实际显示绿色画面。禁止转发时保持禁止，未自动开启解密或改为转码。

证据目录：`tmp/fntv-no-proxy-20261122-hwefzB/`。

- `native-direct-info.jpg`、`native-proxy-info.jpg` 及对应 TXT：客户端文件信息中的方式标签。
- `native-final-direct-frame.jpg`、`native-final-direct-frame.txt`：最终普通 HLS 直链画面。
- `native-aes-direct-error.txt`、`native-aes-proxy-frame.jpg`：受控 AES-128 直连错误与转发画面对照。
- `final-direct-evidence.json`、`native-requests.jsonl`、`media-requests.jsonl`：最终快照、协议和媒体请求。日志包含排查中的其他试验阶段，登录头计数为最终阶段的筛选结果。

临时客户端、服务端及媒体夹具已停止；对应三个本地端口均无监听。本次没有连接用户的实体 iPhone 或生产服务，未把受控验收推广为全部外部来源可播放。
