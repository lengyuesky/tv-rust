# 镜像构建故障与流程优化

日期：2026-11-19（Asia/Shanghai）。

## 故障证据

[修复提交 ff3cf31 的工作流](https://github.com/lengyuesky/tv-rust/actions/runs/44521938183) 在测试任务的“安装原生依赖”步骤停止。Ubuntu 的镜像源连续返回 503；安装从 20:14:18 持续到 20:34:05，触发任务超时。Rust 检查、网页构建和 Docker 任务均没有开始。

[前一次成功工作流](https://github.com/lengyuesky/tv-rust/actions/runs/44509130329) 总耗时约 13 分 8 秒，其中同一系统安装步骤用了 10 分 34 秒。两台 Docker 任务分别约 48 秒和 55 秒。这里的慢步骤是重复系统安装，不能将这次取消认定为 Rust 编译或镜像内容错误。

## 最终流程

1. 检查任务使用 runner 已有的编译器、CMake 和 pkg-config；FFprobe 使用已在 AMD64 样本验证的 BtbN 8.1.3 共享库构建，固定长期保留的月度归档及 SHA-256 并单独缓存，只用于受控素材测试。获取步骤限定两分钟，并保留格式、Clippy、Rust 和网页测试。
2. 网页构建一次，上传不压缩的 `web-dist` 产物。
3. AMD64 和 ARM64 两台免费标准 runner 并行原生构建，各使用所有可用 CPU。Dockerfile 的 `web-output` 阶段在 CI 中由共享网页产物替代，普通本地构建仍会从网页源码开始。
4. 单架构使用一次 Buildx 构建，同时导出本地 Docker 镜像和远端未标记摘要，取消此前为了推送再调用一次构建的流程。两种架构通过容器启动检查后，再合并并更新 `latest`、提交或版本标签。
5. Rust 依赖继续保留独立分层和各架构 GHA 缓存。没有改变 release 优化，也没有通过修改编译环境变量破坏现有 Rust 检查缓存。缓存导出限定三分钟，导出失败不使已完成的构建失败。

仅修改文档或 README 的提交不触发镜像重建；版本标签和手动触发仍可构建。

镜像启动检查整理到 `scripts/smoke-image.sh`，覆盖架构、UID 10001、只读文件系统、健康与首次启动状态、网页和 FFprobe，并自动清理临时容器与数据卷。

## 免费资源范围

仓库当前为公开仓库。GitHub 官方标准 runner 表确认：`ubuntu-24.04` 与 `ubuntu-24.04-arm` 各提供 4 核、16 GB 内存。构建矩阵最大并行数为 2，合计 8 核、32 GB，使用原生架构，不启用模拟编译或收费的大型 runner。冷构建仍需获取系统包与 Rust 依赖；缓存命中后的时间不能冒充冷构建性能。

依据：[GitHub 托管 runner 规格](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)、[单次构建的多导出支持](https://docs.docker.com/build/exporters/#multiple-exporters)。
